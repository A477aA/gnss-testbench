# План тестирования ПО приёма и анализа NMEA-потока GNSS-приёмника

## 1. Объект тестирования

ПО, которое принимает NMEA 0183 с последовательного порта GNSS-приёмника, разбирает
сообщения и оценивает качество навигационного решения: время до решения, стабильность
RTK, точность относительно опорной точки, целостность потока.

**В рамках:** сообщения GGA, RMC, GSA, GSV, VTG (включая расширения NMEA 4.10),
потоковый приём, расчёт метрик, критерии приёмки, отчёты, CLI.

**Вне рамок:** бинарные протоколы (UBX, RTCM), конфигурирование приёмника, PPP,
вертикальная точность.

## 2. Уровни тестирования

| Уровень | Что проверяет | Где | Когда |
|---|---|---|---|
| Unit | Отдельные функции: контрольная сумма, поля, сообщения, метрики | `tests/unit` | Каждый коммит |
| Property-based | Инварианты на случайных входах: парсер не падает, декодер не зависит от нарезки потока | `tests/property` | Каждый коммит |
| Интеграционный | Путь «эмулятор → pty → pyserial → декодер → анализ → приёмка» | `tests/integration` | Каждый коммит |
| Приёмочный | Сценарии с заданными критериями, в том числе негативные | `scenarios/` + `criteria/` | Каждый коммит, матрица в CI |
| Аппаратный (HIL) | Реальный приёмник на стенде | `tests/hardware` | Вручную и по расписанию на раннере `gnss-bench` |

## 3. Техники тест-дизайна

- **Эталонные данные** — классические строки из описаний NMEA 0183 с известной контрольной суммой.
- **Классы эквивалентности** — полушария, все значения качества решения (0–8) и невалидные, статусы RMC, режимы GSA.
- **Граничные значения** — широта ±90°, долгота ±180°, минуты 59.9999/60, время 23:59:59.99/24:00, год 79/80 (смена века), азимут 359/360, SNR 99/100, переход через полночь UTC.
- **Тестирование переходов состояний** — NO_FIX → GPS → RTK_FLOAT → RTK_FIXED и обратно (потери фиксации).
- **Внесение дефектов (fault injection)** — пропадание данных, битые контрольные суммы, оборванные строки, мусор в порту, искажённые байты, ложная фиксация.
- **Фаззинг / property-based** — случайные тексты и байты, случайная нарезка потока.
- **Негативное тестирование самого стенда** — сценарии с дефектами обязаны провалить приёмку.

## 4. Окружение

| Окружение | Состав |
|---|---|
| Виртуальный стенд | Linux, Python 3.11+, эмулятор приёмника на pty |
| Аппаратный стенд | Раннер GitLab с тегом `gnss-bench`, приёмник по USB (`/dev/ttyUSB0`), антенна на открытом небе, RTK-поправки по NTRIP |

## 5. Критерии приёмки RTK (статика, открытое небо)

Файл: `criteria/rtk_static.toml`.

| Метрика | Порог | Обоснование |
|---|---|---|
| TTFF | ≤ 60 с | Холодный старт многосистемного приёмника |
| Время до RTK fixed | ≤ 120 с | Типичная сходимость RTK при коротком базисе |
| Доля RTK fixed после фиксации | ≥ 95 % | Пропущенные эпохи считаются как «не fixed» |
| Потери RTK fixed | 0 | В статике на открытом небе срывов быть не должно |
| Скачки координат > 0.5 м | 0 | Признак ложной фиксации неоднозначности |
| CEP95 | ≤ 3 см | Точность RTK в плане, только по эпохам RTK fixed |
| Максимальный разрыв потока | ≤ 2 с | Ни одной пропущенной секунды подряд |
| Медиана PDOP | ≤ 2.5 | Геометрия созвездия |
| Доля битых строк | ≤ 0.1 % | Целостность канала связи |

## 6. Критерии начала и окончания

**Начало:** сборка проходит `ruff` и `mypy --strict`.

**Окончание:**
- все unit-, property- и интеграционные тесты зелёные;
- позитивные сценарии проходят приёмку, негативные — проваливают;
- открытых дефектов с серьёзностью Critical или Major нет.

## 7. Метрики процесса

- Покрытие веток кода (цель ≥ 90 %, сейчас ~96 %).
- Число тестов по уровням и время прогона конвейера.
- Найденные дефекты по серьёзности и этапу обнаружения — см. [bug-reports.md](bug-reports.md).

## 8. Риски

| Риск | Мера |
|---|---|
| Эмулятор не повторяет поведение реального приёмника | Аппаратный job на стенде по расписанию; логи с реального приёмника добавляются как регрессионные данные |
| Нестабильные (flaky) тесты на pty из-за таймингов | Детерминированный seed, ускорение времени, запуск вещания только после открытия порта |
| Устаревание порогов приёмки | Пороги хранятся в TOML под версионным контролем и меняются через merge request |
